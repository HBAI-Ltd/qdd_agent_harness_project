# 通用技能方法论 · 用 HID 键鼠桥操作 GUI（设备无关）

> 适用：通过外部键鼠桥（BLE HID / 远程键鼠 / 硬件注入）操作任意 GUI —— Android 手机/平板、
> 车机、电视、工控屏、远程桌面都可能。本文只讲方法，不含某台设备的坐标、增益或产品细节。
> 设备相关参数一律在「设备画像」阶段实测得出，不写入方法论。

> 手机技能适配：本文与 [SKILL-v2.md](SKILL-v2.md)、[PROMPT.md](PROMPT.md)、[CAPABILITIES.md](CAPABILITIES.md) 一起加载。Android 返回仍沿用系统 Back → Home → 最近任务，不采用本文通用示例中的页面内返回。校准接口与状态以当前 MCP 实际返回为准，禁止沿用历史设备的增益、坐标和单步上限。中文输入继续使用已支持的新版 ESP 加密 BLE 文本通道和 QDD 输入法，详见主技能，不受下文对传统 HID 能力的概括限制。

---

## 一、第一性原理：桥只给你位移，所以一切都要闭环

传统 HID 键鼠通道的基本动作是：**相对移动、按下/抬起、按键**；新版另有中文文本通道。桥本身不知道光标在哪，也不知道屏幕上发生了什么，服务端回报的位置也可能只是估计。
因此任何"点到某个像素"都是**估计量**，必须由**可观测反馈**收敛：

```
意图 ──→ 动作 ──→ 观测 ──→ 判读 ──→ (不满足) 修正 ──→ 动作 …
                 └──────────── 指针：改坐标      └────────── 状态：改策略
```

由此推出四条**不可违反**的推论：

| 推论 | 含义 |
|---|---|
| **P1 没有观测就不算完成** | 动作返回 `completed` 只代表指令下发；只有画面/计数的变化才算"发生了" |
| **P2 两阶段必须分离** | "定位"与"点击"是两次独立动作，中间必须有一次观测；合并=放弃观测 |
| **P3 估计会漂** | 增益、加速、边缘吸附、页面刷新都会让估计失效；漂移只能靠周期复观测消掉 |
| **P4 非幂等操作不能重试** | 发送/提交/支付一旦"不确定"，只能回读状态，不能补动作 |

## 二、铁律（全部来自事故，不是最佳实践）

| # | 铁律 | 违反后的真实后果 |
|---|---|---|
| **0** | **点击前必看「目标点 ±N 窗口的实拍裁剪」+ 整屏状态图** | 坐标对了照样点错控件；或点在已被替换/轮播的页面上 |
| **1** | **定位与点击分离**，中间必须观测 | 累积误差可达数百 px，点到相邻控件 |
| **2** | **每个导航动作后等 ≥0.5–1.4s 再判读** | 截到转场旧帧 → 误判"没生效" → 补点 → 多退一层/重复提交 |
| **3** | **只有"动作从未开始"才允许重试** | 已下发但图像超时时重放 = 重复执行 |
| **4** | **非幂等操作绝不补动作**，只回读状态 | 重复评论/重复发送 |
| **5** | **坐标结论必须带证据**（图或计数/文案） | 无法复盘，也无法把经验写成能复用的事实 |

> 铁律 0 的判据是三件事同时成立：**新帧 + 目标控件在窗口图里被十字压住 + 整屏仍是该状态的页面**。

## 三、闭环控制：三层互补观测

| 层 | 观测手段 | 可信度 | 何时用 |
|---|---|---|---|
| L1 | **坐标回读**：桥/服务端返回的 pointer（`hover`、`actionResult`） | 数值线索，须检查 `positionEstimated`；估计值不能证明真实光标位置 | 每次定位后与目标比差，容差按控件大小和实测误差设置，不套用别台设备的固定值 |
| L2 | **窗口实拍**：目标点 ±N 的全分辨率裁剪（放大 + 十字） | 高（能证明"是什么控件"） | **每次点击前**；同时可量出渲染偏移 |
| L3 | **帧差**：连续两帧差分找变化块（光标/摘要/计数） | 中（依赖运动） | 需要定位真实光标位置时；静止页面会失效 |

三条关键的工程事实：

1. **光标可能不入镜**：系统可能在静止后隐藏光标，是否被采集必须按设备实测。坐标（L1）+ 窗口内容（L2）用于交叉检查；`android_preview_tap` 的十字是模拟目标，不移动真实鼠标、不点击，不能证明物理落点。若只有估计坐标，不能声称已目视确认真实光标；先使用当前 MCP 支持的实测校准/观测能力，仍无法建立定位依据时停止点击并报告。
2. **帧差会给出两个残影**：移动前后各一个。必须按本机实测误差排除**旧位置附近的变化块**，
   否则会一直读到上一位置，表现为"驱动原地打转、坐标不前进"。
3. **窗口图的十字必须画在真实点击点**上，而不是图片中心：靠近屏幕边缘时裁剪框会被夹住，
   画在中心会凭空制造偏移，把正确的落点判成错误。

## 四、设备画像（换设备必重做，10 分钟）

不要继承任何上一台设备的数字。逐项实测、逐项记录：

| 项 | 怎么测 | 记入画像 |
|---|---|---|
| 分辨率/旋转 | 首帧的 width/height/rotation | 坐标系基准 |
| **增益**（px per 位移单位） | 归零 → 单次已知位移 → 帧差读光标落点 → 算出 px/计数 | 换算的唯一依据 |
| **线性区间** | 逐步加大单步位移，看落点是否仍线性 | 单步上限（超了会加速/丢步） |
| **光标可见性** | 移动后截图 + 帧差 | 能否用 L3；不能就只用 L1+L2 |
| **渲染偏移** | 窗口图里"真实光标"与"十字"的距离 | 点击时的系统偏差补偿量 |
| **点击副作用** | 点完后光标是否移动、移动多少 | 决定"每次点击都要重新定位"还是"可复用" |
| 滚动方式 | 滚轮 vs 拖拽；拖拽起点须避开系统手势区 | 翻页原语 |
| 系统 chrome 占用区 | 手势条/Dock/悬浮球覆盖哪些 y 区间 | 这些坐标不可用 |

**校准值的物理意义**：`校准 = 每像素多少位移单位 = 1/增益`。填错可能不报错，却让坐标整体偏移
——这是典型的"静默错误"。优先使用当前服务支持的无点击校准/移动观测来验证；只有目标无副作用且已确认可安全操作时，才用单次测试点击补充验证。

## 五、页面状态机：先认状态，再谈坐标

坐标只在某个状态下有效。所以流程永远是 **认状态 → 取目标 → 动作 → 复核状态**。

```
识别锚点（稳定区域签名，不是内容）
   ↓
状态 = f(锚点集合)        例：列表页 = 顶栏 + 多列卡片 + 底栏；详情页 = 作者栏 + 动作行
   ↓
该状态下的目标坐标表      固定元素查表 / 列表元素现测
   ↓
动作 → 复核：锚点是否变成目标状态？（以计数/文案/页面为准）
   ↓
不是目标状态？→ 先判是"未生效"还是"变了别的状态"（漂移），再决定重试或重定位
```

两条经验：

- **要固化的是"锚点"，不是"截图"**：内容会变（换帖、换商品、换推荐），锚点不会。
- **列表类目标必须现测**：位置随刷新漂移，固化的历史坐标必然失效（这点常被低估）。

## 六、动作原语的选型（按可靠性排序）

1. **最稳：画面内已有的同一实体**（同一个链接/按钮的另一个入口）——优先复用它，而不是计算新坐标。
2. **次稳：状态机内的固定锚点**（顶栏返回、底部动作行）——坐标稳定，但要避开系统 chrome 区。
3. **再次：现测的列表元素** —— 必须配合铁律 0 的窗口确认。
4. **最差：跨状态的记忆坐标** —— 只在状态完全一致时才成立。

点哪里也很关键（通用）：**点控件中心的"非文字区"**。点文字容易触发长按菜单/选中，
点图标边缘容易被相邻控件抢走；卡片就点封面中段，按钮就点文字居中处。

## 七、失败分类法（先分类，再决定要不要重试）

任何"点了没反应"都先归到四类之一，**不要直接重试**：

| 类别 | 表现 | 判定手段 | 处置 |
|---|---|---|---|
| **链路类** | 所有动作都失败/超时/paused/重连中 | 状态查询、动作返回文本 | 等链路恢复、重新武装；**不要在链路问题上怀疑 App** |
| **未武装类** | 键盘输入无效果或接口明确拒绝 | 输入接口的显式错误文本及 `actionStarted` 等派发状态 | 恢复武装；仅当明确证明原动作未开始/未派发时，才允许单次重新执行。仅凭画面没变化不能重放 |
| **定位类** | 动作成功但落点偏、点到别的控件 | 窗口图/坐标差 | 重新定位，不补点 |
| **状态类** | 页面已变（轮播/刷新/弹窗） | 整屏图锚点不符 | 重新取帧、重走状态机 |

**通用升级路径**：选择当前设备已验证的导航入口，每次只执行一个动作并观察；本手机技能固定采用系统 `back` → Home → 最近任务，不使用页面内返回箭头。
**禁止**：`back` 与页面内返回箭头连用（会多退一层）；同一非幂等动作补第二遍。

## 八、凭据与可复现

每次动作至少留三样东西：**确认图（点击前）**、**效果图（点击后）**、**判读依据（计数/文案）**。
文件名带时间戳即可，不需要额外工具。判断标准永远是**画面与计数**，不是动作返回值。

事故复盘的最小模板：

```
期望状态 → 实际状态 → 差别 → 归因（四类失败之一）→ 下次如何用观测提前发现
```

## 九、一页速查

```
① 认状态（锚点） ② 定位（只移动，记坐标） ③ 看窗口图（十字压住目标？整屏还是该状态？）
④ 点击（原地） ⑤ 等 ≥0.5s ⑥ 复核（计数/文案/锚点）
   └ 没变：先归类（链路/未武装/定位/状态），再决定重试或重定位；非幂等只回读
换设备：重测 增益/线性区间/光标可见性/渲染偏移/点击副作用/滚动方式/chrome 占用区
任何时候：坐标结论必须带图；动作返回值不算证据
```

**这套方法之所以通用**：它不假设具体设备、具体 App、具体坐标，只依赖三件事是恒定的 ——
**动作可观测、状态可识别、失败可分类**。任何 GUI 自动化环境都满足这三条。
